# Porto Ajuda admin authentication audit

**Scope:** read-only inspection on 2026-11-17. No login was submitted and no application, configuration, database, or process state was changed. This report is the only new file.

## Current flow

1. The public modal in `public/components/acesso-admin.js` posts credentials to `POST /admin/auth/challenges`.
2. `AdminAuthenticationService.iniciar` checks admin eligibility and persists an `ISSUING` challenge plus encrypted outbox deliveries in `admin_auth_challenges` and `admin_auth_deliveries`. The current source creates an email delivery and, when `ADMIN_SMS_VERIFICATION_ENABLED=true`, an SMS delivery.
3. `AdminAuthDeliveryWorker` polls the outbox (default 1,000 ms), claims rows with database coordination, sends email through `EmailService` or SMS through `SmsService`/`SmsMaisClient`, and records `SENT`/`FAILED`. The queue moves a challenge to `PENDING` when all its delivery rows are `SENT`. SMS provider exceptions are deliberately logged without exception details.
4. The modal verifies email then SMS with `POST /admin/auth/challenges/{id}/verify`. The service locks the challenge row, checks hashed codes and expiry/attempt limits, writes verification/audit state, and calls `AdminPrivilegedSessionService.emitir` in the same transaction. SMS requirement is derived from whether that challenge has an SMS delivery row. `202` with `nextFactor=DELIVERY` means the challenge remains `ISSUING`; the same code is not consumed by that branch.
5. Successful verification persists `admin_privileged_sessions`, returns `204`, and issues the HttpOnly `PA_ADMIN_SESSION` cookie scoped to `/admin`. `AdminSessionAuthFilter` clears any ordinary-user security context on `/admin`, validates only this cookie against the persisted admin session, and supplies the user's authorities plus `ADMIN_SESSION`.
6. `GET /admin/auth/session` checks the session. The overview endpoint `GET /admin/dashboard/overview` requires `DASHBOARD_READ`. Logout is `POST /admin/auth/logout`; session lifetimes are two hours absolute and twenty minutes idle.

Related persistence also includes `admin_security_audit_events` and `admin_auth_controls` (account/IP lockouts and rate controls). Main configuration: `ADMIN_SMS_VERIFICATION_ENABLED`, `SMSMAIS_ENVIRONMENT`, `SMSMAIS_TOKEN`, `APP_COOKIES_SECURE`, `ADMIN_AUTH_DELIVERY_POLL_MS`, `APP_ADMIN_AUTH_DELIVERY_WORKER_ENABLED`, `ADMIN_RBAC_ENFORCEMENT_ENABLED`, `PORT`, and database/email settings. `application.properties` imports `./.env` and `../.env`; OS environment variables take precedence over file/default values in Spring Boot.

## Module compatibility

Admin endpoints use `AdminPermission` checks, including dashboard read; NGO representative review (`NGO_VERIFICATION_READ/REVIEW`); Sophie human-support inbox (`SUPPORT_READ/MANAGE`); reports (`REPORT_READ/REVIEW/RESOLVE`); moderation and entity/points (`ENTITY_READ`, `POINTS_READ/ADJUST`); appeals (`APPEAL_READ/RESOLVE`); and administrative/session management permissions. Other content and organization routes require their corresponding `CONTENT_*` and `ORG_*` permissions. Keep role-to-permission assignment and `AdminAuthorizationService` checks unchanged. The ordinary-user JWT filter remains separate; on `/admin`, the admin filter clears that context and authenticates only `PA_ADMIN_SESSION`. Logout revokes the credential and clears the cookie; expiration/revocation is checked server-side on requests.

Exact role assignments for the target account were not verified because no administrative session was established. `ADMIN_RBAC_ENFORCEMENT_ENABLED` currently defaults false; endpoint-level permission annotations still exist, but the effect of the flag on each authorization helper should be reviewed before deployment rather than changing it as part of MFA work.

- Logout revokes the server session and clears the cookie; idle and absolute expiry are enforced.
